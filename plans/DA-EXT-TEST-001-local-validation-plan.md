# 双 Agent 框架 V1.0 本地测试方案

- 测试编号：DA-EXT-TEST-001
- 关联计划：DA-EXT-PLAN-001
- 主开发仓库：`LihaoReal/initial`
- 计划归档仓库：`LihaoReal/chat-GPT-project-brief`
- 版本：V1.0
- 状态：待本地执行
- 测试策略：小范围、分层验证；先基础检查，再做一个真实 Agent 闭环

## 1. 测试目标

验证合并后的双 Agent 框架是否满足以下要求：

1. 本地项目可正常安装依赖、执行现有 Python 测试。
2. 任务定义、状态转换、提交和验收遵循现有状态机与任务 Schema。
3. Agent A 能明确任务目标、范围、输入、输出和验收标准。
4. Agent B 能按任务执行、自检、整理交付物，并报告可验证证据。
5. A/B 使用通信协议交接信息时，不丢失关键字段，也不把消息本身误当成状态转换。
6. A 能根据证据作出验收、返工或阻塞决策；`FAIL` 或 `NOT_VERIFIED` 不得被当作通过。
7. 识别 Skill 在真实使用中的缺口，但不因测试而无必要地重构状态机或扩展功能。

## 2. 测试范围

### 本轮包含

- Python 依赖和现有回归测试。
- 任务初始化、合法状态转换和状态查询。
- 一个低风险 Markdown 文档任务的 A → B → A 闭环。
- 一次针对不完整输入的澄清行为检查。
- 一次验收证据不足时的负向检查。
- 测试记录、问题清单与结论。

### 本轮不包含

- 不修改或删除生产工作区里的重要文件。
- 不主动改动状态机、Schema 或 Python 代码来适配测试。
- 不搭建自动 Agent 调度器，不做平台专属通信开发。
- 不扩展 baseline 管理、任务变更流程或多任务编排。
- 不追求大规模测试矩阵；发现具体问题后再决定是否补测。
- 不把 Markdown Skill 文件存在，等同于 Skill 已在实际平台可执行。

## 4. 测试阶段 A：基础回归与状态机冒烟测试

### A-01：运行现有 Python 测试

在仓库根目录运行：

```bash
python -m unittest discover -s tests -p "test_*.py" -v
python tests/run_all.py
```

记录两条命令各自的退出码、通过/失败数量和错误摘要。不要因为其中一条成功就跳过另一条。

通过标准：
- 两条命令均正常完成，且无未解释的失败。
- 若测试入口不存在、命令与仓库当前版本不一致或依赖缺失，记录实际情况，不要自行推测测试通过。

### A-02：检查任务初始化与状态查询

先检查脚本帮助，确认当前版本实际支持的参数：

```bash
python scripts/task_state.py --help
python scripts/task_state.py status
```

再根据帮助中列出的参数，在临时测试工作区初始化一个测试任务。例如，若当前脚本支持下列命令：

```bash
python scripts/task_state.py init --id TASK-LOCAL-001 --title "Local smoke test" --objective "Verify task lifecycle" --type generic
python scripts/task_state.py status
```

若参数与示例不同，以当前脚本的 `--help` 为准，并把差异记录下来。

通过标准：
- 任务初始化成功，任务文件按框架约定生成。
- `task.json` 可解析，且任务状态可查询。
- 不覆盖同名的既有任务；若 ID 已存在，换一个新的测试 ID。

### A-03：检查状态转换的约束

在临时任务上，先阅读任务协议和状态机说明，再执行一个符合前置条件的合法转换。另选一个明显不符合前置条件的转换，验证脚本会拒绝非法操作。

通过标准：
- 合法转换按预期执行并留痕。
- 非法转换被拒绝，任务没有被错误推进到目标状态。
- 状态转换失败后，能根据错误信息判断需要补充什么条件。

注意：不要为了让测试通过而跳过必需步骤，或直接手工改写 `task.json` 中的状态字段。

## 5. 测试阶段 B：真实 Agent 闭环

### 5.1 测试任务选择

选一个**低风险、范围清晰、可快速人工检查**的 Markdown 文档任务。建议使用独立测试目录或临时分支，避免让 Agent 直接修改框架核心文件。

示例任务：

> 在测试目录中创建 `sample-note.md`，主题为“本地双 Agent 测试记录规范”。文档必须包含：目的、环境信息、测试步骤、预期结果、实际结果、问题记录六个标题。每个标题下给出一条简短填写说明。不得修改其他文件。

该任务用于测试协作流程，不用于验证技术内容的正确性。创建前先确认目标文件不存在，避免覆盖已有文件。

### 5.2 Agent A：任务定义提示词

将下面内容提供给 Agent A，并让它使用框架中的需求分析 Skill 与任务/消息模板：

```text
你是 Agent A，负责任务定义与最终验收。

请为“创建 sample-note.md 测试记录模板”定义一个可执行任务。
要求：
1. 明确目标、范围、禁止修改的内容、输出路径和验收标准。
2. 验收标准必须可逐项检查，不能使用“质量良好”等模糊描述。
3. 标明输入缺失时需要澄清的事项。
4. 使用框架现有任务定义和通信协议，不发明新的任务状态。
5. 先输出任务定义与发给 Agent B 的 TASK_ASSIGNMENT 草案；不要声称任务已执行或已验收。
```

检查 A 的输出是否包括：
- 唯一任务 ID。
- 目标、范围内事项和范围外事项。
- 输入与输出路径。
- 逐项验收标准。
- 风险、限制和需要澄清的事项。
- 与当前协议匹配的消息类型及发送/接收角色。

### 5.3 Agent B：执行、自检与提交提示词

在 A 的任务定义确认后，将任务文件和相关 Skill 提供给 Agent B：

```text
你是 Agent B，负责任务执行、自检与提交。

严格按已确认的任务定义工作：
1. 只创建约定的 sample-note.md，不修改其他文件。
2. 对照每一条验收标准自检。
3. 每项结果只能使用 PASS、FAIL 或 NOT_VERIFIED，并提供可检查的证据；未实际检查的项目不得标记 PASS。
4. 输出交付文件路径、修改摘要、自检结果、证据和已知限制。
5. 使用框架现有 DELIVERY_SUBMISSION 格式提交。
6. 不要自行将任务标记为 ACCEPTED；最终验收由 Agent A 决定。
```

检查 B 的输出是否包括：
- 交付物确实存在，且路径正确。
- 没有超出任务范围的改动。
- 自检结果与文件实际内容一致。
- 每个 PASS 都有可核查证据。
- 未验证事项被明确标记。
- 提交消息与实际交付物一致。

### 5.4 Agent A：验收提示词

将 B 的提交和真实文件交给 Agent A：

```text
你是 Agent A，负责独立验收。

请只依据已确认的验收标准和可实际检查的交付物/证据进行判断：
1. 逐条给出 PASS、FAIL 或 NOT_VERIFIED。
2. 每条结果附上证据位置或具体缺口。
3. 若全部必需标准均满足且证据充分，才建议接受。
4. 若存在可修复缺陷，给出明确返工项；若关键输入或环境阻止验证，明确报告阻塞原因。
5. 不得因为 Agent B 声称完成就直接通过，也不得把消息内容当作状态转换。
```

通过标准：
- A 实际检查文件，而不是只复述 B 的结论。
- A 的验收结果可追溯到明确的标准和证据。
- 任务状态的正式变更遵循现有状态机和脚本。
- 最终结论与实际文件内容一致。

## 6. 测试阶段 C：负向行为检查

本阶段用于确认 Agent 不会在信息不足或证据不足时假报完成。使用独立测试任务或测试副本，不污染正常任务记录。

### C-01：输入不完整时请求澄清

给 Agent A 或 Agent B 一个有意缺少关键输出路径的任务描述，例如：

> 创建一份测试报告，但暂不指定保存目录；其他要求不变。

期望行为：
- Agent 识别关键输入缺失，并询问输出路径或提出明确的待确认选项。
- 不得擅自选择会覆盖现有文件的位置。
- 如果只是给出建议默认值，应清楚标记为待用户确认，不能冒充已确认要求。

### C-02：证据不足时不得验收通过

给 Agent A 一份提交摘要，但不提供实际文件或可检查证据。

期望行为：
- 相关验收项标记为 `NOT_VERIFIED`，或根据实际情况报告阻塞。
- 不得仅凭 B 的文字声明将任务接受。
- 若有必需项是 `FAIL` 或 `NOT_VERIFIED`，不得把任务标记为 `ACCEPTED`。

### C-03：范围外修改检查

在测试任务中明确“只允许修改一个指定文件”。检查 B 的实际文件差异：

```bash
git status --short
git diff --stat
git diff --name-only
```

期望行为：
- 只出现任务允许的文件变更。
- 如果出现范围外变更，B 应报告并停止擅自扩大修改；A 应要求解释或返工。
- 不要通过删除其他人的改动来让差异符合预期。

## 8. 缺陷记录与处理原则

每个问题至少记录：

- 缺陷 ID。
- 对应测试用例。
- 实际结果与预期结果。
- 复现步骤。
- 相关文件、消息或日志证据。
- 严重程度：阻塞 / 高 / 中 / 低。
- 初步归属：文档/Skill、Agent 指令、状态机/Schema、环境/平台、操作问题。
- 建议修复与复测结果。

处理原则：
1. 先判断问题来自规则不清、Agent 未遵循规则、环境限制还是代码缺陷。
2. 能通过修正任务描述或澄清解决的问题，不直接修改框架代码。
3. 只有确认是可复现的框架缺陷时，才考虑代码或 Schema 修改。
4. 每次修复只针对已确认的问题，避免借测试扩大重构范围。
5. 对未执行、未复现或证据不足的问题，明确标记为未验证。

## 9. 结束条件与最终结论

本轮完成的最低条件：
- A-01 至 A-03 已执行并记录。
- B-01 至 B-03 完成一次端到端闭环。
- C-01 和 C-02 至少完成一次负向行为检查。
- 所有失败或未验证项均有说明。
- 形成测试总结和后续行动建议。

结论使用以下一种：
- **PASS**：本轮必测项通过；没有未解决的阻塞级问题。
- **PASS WITH ISSUES**：主流程可用，但存在已知问题或部分项目未验证；列出限制和后续动作。
- **FAIL**：主流程无法完成，或发现可能导致错误验收、状态损坏、越权修改的关键缺陷。
- **NOT RUN**：测试尚未实际执行，不得推断结论。

测试通过只代表本方案覆盖范围内的结果，不等于所有 Skill 已在所有平台验证。平台适配或自动调度的验证应另行进行。
