# 双 Agent 基础 Skill 与通信协议扩展开发计划书

- 计划编号：DA-EXT-PLAN-001
- 版本：V1.0
- 状态：已归档，按阶段实施
- 创建日期：2026-10-30
- 主开发仓库：`LihaoReal/initial`（generic-dual-agent）
- 计划归档仓库：`LihaoReal/chat-GPT-project-brief`
- 适用范围：平台无关的通用双 Agent 任务开发与执行框架

## 1. 背景与目标

现有双 Agent 框架已在用户的本地使用场景中运行，当前没有明显阻碍日常使用的故障。本阶段不继续进行大范围审查或重构，而是将重心转向可复用能力建设：明确 Agent A、Agent B 的基础 Skill，整理双方共用的通用 Skill，并制定轻量、稳定的 Agent 间通信格式，以减少信息遗漏、交付歧义和重复沟通。

本计划面向通用双 Agent 框架，不将协议绑定到 WorkBuddy 或某一特定平台。WorkBuddy 只是当前使用环境之一；平台特定的配置和传输适配不属于本阶段范围。

## 2. 目标与成功标准

### 2.1 目标

1. 明确 A/B 的角色边界与基础 Skill 清单。
2. 建立统一 Skill 编写模板，保证每个 Skill 的触发条件、输入、步骤、输出、验证和异常处理清晰。
3. 定义 Agent 间核心消息类型和最小必填字段。
4. 使通信消息与现有任务状态机、任务协议、提交和验收机制保持一致，避免另造一套状态系统。
5. 通过真实任务和最小回归验证逐步完善，不以扩大测试规模或重构既有代码为目标。

### 2.2 成功标准

- A/B 职责与 Skill 清单没有明显重叠或责任空缺。
- 任务下发、澄清、进度、交付提交、验收结果、阻塞报告均有明确格式。
- 交付消息能关联 task_id、交付物、逐项验收结果和证据；无法验证的项目不得伪装为通过。
- 消息格式不替代现有状态机；状态仍以任务状态权威源为准。
- 新增文档、模板和 Skill 指引与现有协议一致，且每个阶段执行最小回归检查。
- 所有变更通过独立分支和 Pull Request 审查，不直接修改主开发仓库 main 分支。

## 3. 设计原则

1. **平台无关**：协议描述语义、字段与交接规则，不规定某个客户端的专属功能。
2. **最小可用**：先建立少量高价值 Skill 与核心消息类型，按实际任务迭代。
3. **角色与 Skill 分离**：角色文件规定责任和权限；Skill 规定可复用工作方法；协议规定双方如何交换信息。
4. **结构化外壳 + 自然语言正文**：关键字段使用固定名称与受控枚举，技术分析和说明允许自然语言。
5. **证据优先**：结论必须与可检查的交付物、测试结果或记录对应；没有证据时使用 NOT_VERIFIED。
6. **复用现有机制**：不另建状态机，不扩大 baseline 管控，不引入任务变更管理。
7. **最小回归**：不继续无差别扩展测试矩阵；只对新增能力做有针对性的检查，并运行现有最小回归。
8. **可追溯**：需求、协议、Skill、验收用例与 PR 之间应可相互定位。

## 4. 范围边界

### 4.1 本阶段包含

- A/B 基础 Skill 能力矩阵与职责边界。
- 通用 Skill 清单及统一 Skill 模板。
- 通用 Agent 通信协议 V1.0。
- 消息模板/示例与字段校验规则（先以文档约束为主，是否需要程序化校验由实施结果决定）。
- 与现有状态机、任务协议、提交和验收规则的兼容检查。
- 真实任务试用与最小回归记录。

### 4.2 本阶段不包含

- 任务变更管理、关联任务或变更审批流程。
- 扩展完整任务定义 baseline、外部输入文件哈希或 baseline 版本继承。
- 大规模重构 `scripts/task_state.py` 或重新设计状态机。
- WorkBuddy 专属通信机制、平台专属 API 或自动化调度。
- 新增复杂多 Agent 拓扑、父子任务依赖编排。
- 为追求覆盖率而扩大测试范围；现有功能没有具体问题时不做无目的重构。
- 领域专用 Skill（如 BMS WCCA、功能安全标准解读）；这些应作为后续业务扩展。

## 5. 初始 Skill 规划

### 5.1 Agent A 专属基础 Skill

| Skill ID | 名称 | 主要职责 | 主要输出 |
|---|---|---|---|
| A-SK-01 | requirement-analysis | 将自然语言需求转为目标、范围、约束、风险和可验收标准 | 结构化任务定义、待澄清项 |
| A-SK-02 | task-planning | 将任务拆分为有依赖关系、可执行、可验收的步骤 | 执行计划、依赖和检查点 |
| A-SK-03 | deliverable-review | 按既定验收标准审查 B 的提交，记录证据与缺口 | 逐项验收结果、ACCEPT/REWORK/BLOCKED 建议 |

### 5.2 Agent B 专属基础 Skill

| Skill ID | 名称 | 主要职责 | 主要输出 |
|---|---|---|---|
| B-SK-01 | task-execution | 根据已确认的任务定义执行工作，不擅自改变范围或验收标准 | 交付物、执行摘要 |
| B-SK-02 | self-check | 在提交前逐条对照验收标准检查交付物 | 自检结果、证据、未验证项 |
| B-SK-03 | deliverable-packaging | 整理交付路径、文件用途、证据和已知限制 | 标准化提交包/提交记录 |

### 5.3 通用共享 Skill

| Skill ID | 名称 | 主要职责 | 使用说明 |
|---|---|---|---|
| G-SK-01 | file-operation | 安全、可追溯地读取、创建、修改和整理文件 | 遵循任务工作区与权限边界 |
| G-SK-02 | verification | 根据明确标准执行检查并保留证据 | A 用于验收，B 用于自检；结论和权限不同 |
| G-SK-03 | structured-reporting | 生成结构化、可追溯的报告 | 统一摘要、结果、证据、限制和下一步 |
| G-SK-04 | error-handling | 识别信息不足、执行失败、冲突与阻塞 | 说明影响、已尝试动作、需要的决策 |

以上为候选清单。实施时先确认现有角色文件、协议和模板是否已覆盖这些能力；已有内容优先引用或小幅整理，不为“Skill 数量”重复创建文件。第一批优先实现通信协议和 Skill 模板，再选择高价值 Skill 落地。

## 6. 通信协议 V1.0 规划

### 6.1 核心消息类型

| 消息类型 | 方向 | 用途 |
|---|---|---|
| TASK_ASSIGNMENT | A → B | 正式下发已准备好的任务 |
| CLARIFICATION_REQUEST | B → A | 报告缺失、冲突或无法确定的输入 |
| PROGRESS_UPDATE | B → A | 汇报阶段进展、风险与下一步 |
| DELIVERY_SUBMISSION | B → A | 提交交付物、自检结果和证据 |
| ACCEPTANCE_RESULT | A → B | 通知验收结论与依据 |
| BLOCKED_REPORT | A/B → 对方 | 说明阻塞原因、影响及需要的决策 |

### 6.2 通用必填字段

- `protocol_version`
- `message_type`
- `task_id`
- `sender`
- `recipient`
- `timestamp`（如运行环境无法可靠提供时间，则标记为可选，不得伪造）
- `summary`
- `body` 或与消息类型匹配的结构化字段

消息类型可以定义额外必填字段。协议应避免重复传递整个 task.json；以 task_id 和约定的任务文件/路径引用为主。

### 6.3 结果枚举与关键约束

- 检查结果：`PASS`、`FAIL`、`NOT_VERIFIED`、`BLOCKED`。
- 验收决策：沿用框架现有状态和合法转换规则，不自行新增状态。
- `PASS` 必须有可核查证据；没有证据或没有实际执行的检查应为 `NOT_VERIFIED`。
- `FAIL` 或 `NOT_VERIFIED` 不得被整体成功摘要覆盖。
- 消息中的状态声明不能直接改变任务状态；正式状态以现有状态权威源为准。
- 字段缺失、task_id 不匹配或消息内容矛盾时，接收方应请求补充/澄清，不猜测补齐。
- 第一版采用“结构化字段 + Markdown 正文”即可；只有真实使用暴露稳定的解析需求时，才考虑程序化 JSON Schema 校验。

## 7. 实施阶段与交付物

### 阶段 0：计划归档与现状映射

任务：
- 将本计划保存到 `chat-GPT-project-brief`。
- 阅读主开发仓库现有角色说明、任务协议、状态机、验证规则与模板。
- 形成“已有能力 / 缺失能力 / 建议复用或调整”的映射表。

交付物：
- 本计划书归档。
- 内部现状映射记录（放入开发 PR 或项目文档中）。

完成条件：
- 计划可通过固定 GitHub URL 追溯。
- 实施范围与现有协议无冲突。

### 阶段 1：协议与 Skill 设计

任务：
- 设计消息 envelope、消息类型字段和示例。
- 设计统一 Skill 模板。
- 完成 A/B/通用 Skill 能力矩阵，标注复用现有文档的项目。
- 确认与状态机、任务协议、提交/验收规则的一致性。

交付物：
- 《Agent 间通信协议 V1.0》
- 《Skill 编写规范 V1.0》
- 《基础 Skill 能力矩阵与实施映射》

完成条件：
- 每类消息有明确发送者、接收者、必填字段、成功/异常处理。
- 每项 Skill 有唯一职责、输入、输出、验证方法和边界。
- 不重复定义状态机或已有验收规则。

### 阶段 2：第一批 Skill 与模板落地

任务：
- 先落地需求分析、任务执行/自检、交付审查等闭环关键能力。
- 共享能力优先沉淀成通用 Skill 模板或引用文档；避免复制多份规则。
- 为核心消息提供可复制使用的模板。
- 根据需要更新 A/B 角色说明和相关索引，保持规则单一来源。

交付物：
- 第一批 Skill 文档/文件。
- 消息模板与使用示例。
- 更新后的角色说明/文档索引（仅在确有必要时）。

完成条件：
- A 能按模板下发任务并审查提交。
- B 能按模板执行、自检和提交。
- 文件路径、命名、引用关系清楚，没有重复或互相矛盾的规则。

### 阶段 3：真实任务试用与最小回归

任务：
- 选一个文档类任务和一个代码类任务进行试用（如实际条件允许）。
- 观察消息字段是否足够、Skill 是否可复用、是否存在重复沟通。
- 运行与改动相关的最小测试及现有必要回归。
- 记录问题并只修复有证据支持的问题。

交付物：
- 试用记录。
- 问题清单与修复说明。
- PR 验证结果。

完成条件：
- 核心交接信息不丢失。
- 不出现未验证却报 PASS 的情况。
- 既有任务生命周期与状态转换未被破坏。
- 已知限制清晰记录。

## 8. 优先级与执行顺序

1. P0：现状映射，确认现有内容，避免重复建设。
2. P1：通信协议 V1.0 与 Skill 编写规范。
3. P1：A/B/通用 Skill 能力矩阵及第一批核心 Skill。
4. P2：真实任务试用和最小回归。
5. P3：根据使用反馈再考虑程序化校验、更多 Skill 或自动化。

## 9. 风险与控制措施

| 风险 | 控制措施 |
|---|---|
| Skill 与角色说明重复 | 角色只定义职责/权限；Skill 定义可复用步骤；协议定义消息 |
| 消息格式过重，降低自然语言协作效率 | 采用最小必填字段，正文保留 Markdown/自然语言 |
| 协议与状态机不一致 | 以现有状态机为权威，不新增并行状态 |
| Agent 伪报完成或遗漏证据 | 逐项结果 + 证据路径；无证据时 NOT_VERIFIED |
| 一开始创建过多 Skill | 先落地闭环关键 Skill，其余按真实需求扩展 |
| 测试和审查范围失控 | 只执行针对新增能力的检查与最小回归 |
| 平台耦合 | 仅定义平台无关语义，平台适配留到后续单独决策 |

## 10. 变更与决策记录

本计划明确暂不处理：
- 任务变更管理；
- 扩展 baseline 管控；
- 多任务编排；
- WorkBuddy 专属通信实现；
- 大规模代码重构。

如后续实际使用证明某项能力确有必要，再单独评估其收益、成本与范围，不默认纳入本阶段。
