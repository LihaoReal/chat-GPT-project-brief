## 1. 文档目的

本文整理双 Agent 框架学习过程中，围绕 Agent A / Agent B 的角色定义、任务协议和状态管理之外，进一步讨论的七类系统能力。

本文**不是具体 Skill 开发计划，也不是当前框架的功能实现说明**。它的目标是建立对 Agent 系统整体设计的认识，帮助后续判断哪些能力值得建设、何时建设，以及应该由 Agent 指令、任务文件、Python 程序还是运行平台承担。

学习重点：

1. 理解一个可持续运行的 Agent 系统，除角色和任务协议外还需要哪些能力。
2. 区分模型行为约定、持久化数据、程序强制规则和平台能力。
3. 识别当前 Generic Dual-Agent 已经具备的基础，以及尚未实现的能力。
4. 建立后续架构演进的研究顺序，避免过早增加复杂度。

## 2. 当前框架的基础与能力边界

当前框架可以概括为：

- Agent A：负责需求理解、任务定义、任务分配、跟踪和验收。
- Agent B：负责任务执行、自检、交付和问题反馈。
- Python 状态管理程序：负责任务状态转换、角色参数检查、结构校验、文件安全、并发锁、原子写入和审计恢复等。
- 任务文件：保存任务定义、状态、提交信息、验收记录、历史和交付物。
- WorkBuddy：当前 Agent 的运行平台；A/B 之间的实际交接仍需要依赖平台操作、共享文件或人工传递。

### 2.1 已有基础

| 能力 | 当前基础 |
|---|---|
| 任务状态管理 | 已有状态机和状态转换检查 |
| 角色边界 | 已定义 A、B、USER 的职责与部分操作约束 |
| 任务持久化 | 通过任务目录和结构化文件保存状态与记录 |
| 文件安全 | 已有路径检查、原子写入和相关保护 |
| 并发控制 | 已有任务级转换锁 |
| 审计与恢复 | 已有历史快照、摘要校验和恢复检查 |
| 提交与验收 | 已有 submission、自检和 acceptance 相关门禁 |

### 2.2 当前边界

以下事项不能因为文档中有约定，就视为已经由系统强制实现：

- A 自动调用 B，或 B 自动通知 A。
- 后台常驻调度和自动任务队列。
- 跨会话自动恢复 Agent 的完整推理上下文。
- 对模型真实身份进行认证。
- 对所有工具调用实施细粒度权限代理。
- 自动证明交付物的专业技术结论正确。
- 多 Agent 的通用依赖编排和动态扩缩容。

特别注意：任务状态文件保存的是**任务的持久化状态**，并不等于保存了 Agent 当时完整的思考上下文；角色文件中的约束也不等于平台层面的强制权限控制。

## 3. 七类核心系统能力

## 3.1 工作记忆与上下文管理（Memory & Context Management）

### 3.1.1 要解决什么问题

Agent 的一次工作可能跨越多个会话、多个时间段，甚至由不同 Agent 接续完成。

例如：

1. A 创建任务并明确目标和验收标准。
2. B 开始执行，读取资料、形成中间结果。
3. 会话结束或上下文窗口不足。
4. 第二天重新打开任务，B 或另一个 Agent 需要继续工作。

如果系统只依赖原来的对话记录，可能出现信息丢失、重复工作、错误理解或遗漏约束。

因此，需要明确哪些信息应该保留、保存在哪里，以及恢复时如何确认信息仍然有效。

### 3.1.2 三种不同层次的信息

| 信息类型 | 主要内容 | 典型载体 | 生命周期 |
|---|---|---|---|
| 会话上下文 | 当前对话、临时推理线索、即时讨论 | Agent 当前会话 | 短 |
| 任务工作记忆 | 任务目标、当前进度、已完成步骤、待办、阻塞、关键决策 | task.json、执行记录、任务工作区 | 随任务持续 |
| 项目长期知识 | 项目规范、稳定决策、术语、经验和通用背景 | 项目知识库、受控文档 | 长 |

这三者不能混为一谈。对话历史适合保留交互过程，任务记录适合支持任务接续，长期知识库适合跨任务复用。

### 3.1.3 任务恢复时应恢复什么

建议恢复信息至少包括：

- task_id 和当前权威状态。
- 任务目标、范围、约束和验收标准。
- 当前已完成事项及其证据位置。
- 尚未完成事项和下一步建议。
- 已知问题、风险和阻塞。
- 重要决策及其依据。
- 最近一次交付物位置和验证状态。

恢复时不应只读取一段“上次总结”就直接执行。Agent 应先重新读取权威任务文件，核对当前状态、交付物和历史记录，再决定从哪里继续。

### 3.1.4 设计原则

1. **权威源明确**：任务状态和冻结要求以任务文件为准，不以聊天摘要为准。
2. **摘要可追溯**：重要结论应指向原始文件、证据或历史记录。
3. **区分事实与推测**：已验证事实、Agent 判断和待确认事项应分开记录。
4. **避免重复执行**：恢复后先检查已有输出和执行记录。
5. **控制记忆规模**：只持久化后续工作确实需要的信息，不保存大量无用对话内容。

### 3.1.5 对当前框架的意义

当前任务文件和历史记录已经提供了任务级持久化基础，但还需要区分“任务状态恢复”和“Agent 上下文恢复”。前者主要由现有文件和程序支持；后者还需要设计统一的执行摘要、恢复检查和接续约定。

## 3.2 决策机制与自主权边界（Decision Making & Autonomy）

### 3.2.1 要解决什么问题

Agent 不只是执行固定步骤，还会遇到需要判断的情况：

- 输入资料是否足够？
- 两份数据是否存在冲突？
- 是否可以选择替代方案？
- 是否应该继续执行，还是先暂停？
- 是否需要用户批准？

如果没有明确的决策边界，Agent 可能过度自主，也可能遇到任何小问题都反复询问用户。

### 3.2.2 建议区分三类决策

| 决策类型 | 示例 | 建议处理方式 |
|---|---|---|
| 授权范围内的常规决策 | 调整分析顺序、选择无副作用的检查方法 | Agent 自主决定并记录 |
| 影响任务结果但可逆的决策 | 在约束内选择一种实现方案、修改工作区草稿 | Agent 说明依据，按规则执行并留痕 |
| 超出授权或高影响决策 | 改变目标、放宽验收标准、删除重要数据、对外发布 | 暂停并请求用户批准 |

### 3.2.3 决策流程

一个可复用的判断过程：

1. 识别当前需要决定的问题。
2. 检查任务目标、约束和授权范围。
3. 判断是否存在足够信息和证据。
4. 评估决策影响、可逆性和风险。
5. 选择自主执行、请求澄清、请求批准或阻塞。
6. 记录决策、理由、依据和后续影响。

### 3.2.4 关键原则

- Agent 可以在授权范围内自主选择方法，但不能擅自改变任务目标。
- 信息不足时不能把猜测包装成事实。
- 对高风险、不可逆或超授权操作，应设置人工批准点。
- 决策记录应说明“做了什么、为什么、依据是什么”，而不只是记录最终选项。

### 3.2.5 对当前框架的意义

现有 A/B 角色规范和状态机提供了部分决策边界，但仍需区分“模型行为约定”和“程序/平台强制控制”。例如，命令中的 actor 参数只是调用方声明，不构成真实身份认证；授权字段也不自动等于工具权限代理。

## 3.3 可靠性与错误处理（Reliability & Error Handling）

### 3.3.1 要解决什么问题

真实任务执行会遇到工具失败、文件损坏、输入矛盾、计算异常、会话中断和重复提交等情况。可靠系统不仅要定义正常流程，还要定义失败时如何停止、重试、恢复和报告。

### 3.3.2 常见故障及建议处理

| 故障类型 | 例子 | 建议处理 |
|---|---|---|
| 临时性故障 | 网络或工具暂时不可用 | 有限次数重试，记录失败 |
| 输入问题 | 必要数据缺失 | 请求澄清，不自行编造 |
| 数据冲突 | 两份输入给出不同参数 | 暂停受影响步骤，报告冲突 |
| 结果异常 | 计算结果超出合理范围 | 复核输入、公式和单位 |
| 权限不足 | 当前 Agent 无权执行操作 | 停止该操作并报告 |
| 交付失败 | 文件无法生成或无法读取 | 保留已有证据，报告未完成项 |
| 执行中断 | 会话或进程意外终止 | 读取持久化状态后恢复 |
| 重复请求 | 同一提交动作被重复触发 | 检查已有结果，避免重复副作用 |

### 3.3.3 重试策略

重试不应无限进行。建议每类操作明确：

- 是否允许重试。
- 最大重试次数。
- 重试间隔或触发条件。
- 哪些错误不应重试。
- 重试失败后的状态和报告方式。

例如，网络暂时失败可能值得重试；输入参数缺失则不应该重复调用同一个工具。

### 3.3.4 幂等性（Idempotency）

幂等性是可靠系统的重要概念：同一个操作被重复执行时，不应意外产生重复副作用。

例子：

- 同一份提交请求重复到达，不应生成两套重复提交记录。
- 同一个任务恢复执行，不应重复覆盖已经确认的交付物。
- 重复收到交接消息，应先检查任务状态、历史和现有输出。

实现幂等性通常需要稳定的任务/操作标识、执行前检查、结果记录和安全的写入策略。

### 3.3.5 对当前框架的意义

当前框架已有原子写入、任务锁、审计快照和恢复检查，这些主要保护任务文件和状态转换的一致性。它们不能自动解决所有 Agent 工具调用的重试、外部副作用和重复执行问题。后续应先识别真实故障，再决定是否增加操作级幂等机制。

## 3.4 可观测性与运行日志（Observability & Traceability）

### 3.4.1 要解决什么问题

仅知道任务最终是 ACCEPTED 还不够。出现问题时，需要回答：

- 哪个 Agent 在什么时间做了什么？
- 读取或修改了哪些文件？
- 使用了什么工具？
- 哪一步失败？
- 某个结论依据什么证据？
- 人工在哪个环节做过确认？

可观测性让系统行为能够被检查和追溯。

### 3.4.2 建议记录的信息

| 记录类别 | 示例 |
|---|---|
| 任务事件 | 创建任务、状态转换、提交、验收 |
| Agent 活动 | 开始执行、完成步骤、报告阻塞 |
| 工具活动 | 工具名称、输入摘要、执行结果、错误 |
| 文件活动 | 文件路径、创建/修改/读取动作 |
| 决策记录 | 决策内容、理由、依据、批准人 |
| 验证记录 | 检查方法、实际结果、证据位置 |
| 人工介入 | 澄清、批准、否决、修改任务要求 |

### 3.4.3 日志与审计的区别

- **运行日志**：帮助理解执行过程，通常更细、更频繁。
- **审计记录**：记录关键状态变化、责任边界和重要操作，强调可追溯和完整性。
- **交付证据**：证明某个验收结论或技术结果，必须能对应具体检查。

三者相关，但不能互相替代。大量运行日志不一定能证明交付物正确；审计记录也不一定包含足够的技术验证细节。

### 3.4.4 对当前框架的意义

当前框架已有任务 history 和审计快照基础。后续若要提升运行可观测性，可以先统一事件字段和日志粒度，不必立即建设复杂监控平台。记录内容还应注意避免泄露密钥、隐私或不必要的敏感数据。

## 3.5 质量评价与持续改进（Quality Evaluation）

### 3.5.1 要解决什么问题

系统需要可衡量的指标，才能判断 A/B 是否真正提高了工作质量，而不是只增加了流程和文件。

### 3.5.2 可考虑的评价维度

| 维度 | 可观察指标 | 需要注意 |
|---|---|---|
| 需求理解 | 澄清问题命中率、关键需求遗漏数 | 不能只追求少提问 |
| 任务规划 | 任务返工原因、任务拆解完整性 | 任务越细不一定越好 |
| 执行效率 | 完成时间、工具调用次数 | 需结合任务难度比较 |
| 交付质量 | 首次验收通过率、缺陷数 | 通过率不能鼓励降低标准 |
| 可靠性 | 重复执行次数、异常恢复成功率 | 需定义统计口径 |
| 协作质量 | 交接缺失项、澄清往返次数 | 不能单纯追求消息少 |
| 资源成本 | Token、工具调用和运行成本 | 应结合产出价值评估 |

### 3.5.3 指标使用原则

1. 指标必须有明确计算口径。
2. 不要用单一指标代表整体质量。
3. 任务难度和类型不同，不能简单横向比较。
4. 不能为了提高指标而降低验收标准。
5. 指标用于发现改进方向，不应直接等同于 Agent 能力的客观排名。

### 3.5.4 对当前框架的意义

现阶段更适合先积累真实任务样本和返工原因，而不是立即建设复杂评分系统。可以从首次验收结果、返工原因、交接遗漏和重复执行等少量指标开始。

## 3.6 人机协作与权限管理（Human-in-the-loop & Authorization）

### 3.6.1 要解决什么问题

多 Agent 系统并不意味着用户应该退出决策。用户仍需要决定目标、批准高风险操作，并对重要结果进行最终确认。

系统需要明确：哪些操作可自动执行，哪些操作必须留痕，哪些操作需要人工批准。

### 3.6.2 一个简单的风险分级模型

| 等级 | 操作类型 | 建议控制 |
|---|---|---|
| 低风险 | 读取资料、整理信息、生成草稿、运行只读检查 | 可在授权范围内自主执行 |
| 中风险 | 修改任务工作区文件、生成正式交付物、执行可恢复变更 | 执行后留痕，必要时复核 |
| 高风险 | 删除重要数据、改变冻结要求、对外发送或发布、不可逆操作 | 执行前请求用户批准 |

该表是设计参考，不是对任何平台现有权限能力的描述。

### 3.6.3 权限设计的几个层次

- **角色权限**：A、B、USER 分别能做什么。
- **任务授权**：某个任务允许执行哪些操作。
- **工具权限**：运行平台实际上允许 Agent 调用什么工具。
- **资源权限**：Agent 能读取或修改哪些文件、目录和外部资源。
- **批准机制**：哪些操作需要用户确认。

只有当这些层次彼此一致，系统的权限边界才真正有效。Markdown 中写明“禁止删除文件”，不等于平台技术上禁止删除文件。

### 3.6.4 对当前框架的意义

当前框架已经有角色和任务授权方面的约定，但不应把它们描述为完整的权限代理或身份认证。未来如需加强控制，应优先利用运行平台提供的真实权限设置，并对高风险操作增加明确的人工批准步骤。

## 3.7 可扩展性与平台解耦（Extensibility & Platform Independence）

### 3.7.1 要解决什么问题

当前采用 A/B 两个 Agent，未来可能增加专业执行者、独立审核者或知识管理角色，也可能更换运行平台。

如果核心规则和平台操作深度耦合，每增加一个角色或更换平台都可能导致大规模修改。

### 3.7.2 建议理解为四个层次

| 层次 | 主要职责 | 示例 |
|---|---|---|
| 核心协作规则 | 角色语义、任务状态、交接契约、验收原则 | A/B/Reviewer 的责任和状态机 |
| 任务能力层 | 可复用的任务方法与专业能力 | 文档分析、代码实现、技术计算 |
| 平台适配层 | Agent 启动、消息传递、工具权限和会话管理 | WorkBuddy 或其他 Agent 平台 |
| 运行数据层 | 任务文件、交付物、历史和审计数据 | task.json、submission、history |

核心规则尽量保持平台无关；平台差异集中在适配层处理。

### 3.7.3 扩展时需要考虑的问题

- 新增 Agent 是否需要改变现有状态机？
- 新角色是独立职责，还是仅仅是 B 的一种专业配置？
- 多个 Agent 能否并行工作，如何避免文件冲突？
- 任务之间是否存在依赖关系？
- 是否需要独立 Reviewer，如何避免重复验收？
- 更换平台时，哪些规则和数据可以直接复用？

### 3.7.4 对当前框架的意义

当前阶段不必急于增加 C、D、E，也不必立即设计复杂多 Agent 拓扑。应先保证 A/B 的任务闭环清晰、稳定、可验证，再根据真实任务中出现的职责瓶颈决定是否拆分角色。

## 4. 七类能力之间的关系

这些能力不是彼此孤立的：

- 工作记忆让任务可以跨会话持续。
- 决策机制决定 Agent 在什么边界内自主行动。
- 可靠性机制处理失败、重试和重复执行。
- 可观测性记录系统实际做了什么。
- 质量评价利用过程和结果数据推动改进。
- 人机协作确定用户何时介入以及如何授权。
- 可扩展性让系统在增加角色和更换平台时不必推倒重来。

可以把它们理解为一个持续运行的闭环：

```text
用户目标与授权
      |
      v
任务理解与决策
      |
      v
Agent 执行 <----> 工作记忆 / 上下文恢复
      |
      v
可靠性控制与异常处理
      |
      v
交付、验证与验收
      |
      v
运行日志、审计与质量评价
      |
      v
经验反馈与架构改进
      |
      +------> 下一轮任务
```

可扩展性和平台解耦则贯穿整个闭环，决定系统能否逐步增加能力而不破坏已有机制。

## 5. 建议的学习顺序

结合当前框架所处阶段，建议按以下顺序学习：

| 顺序 | 主题 | 学习目标 | 建议产出 |
|---|---|---|---|
| 1 | 工作记忆与上下文管理 | 理解会话、任务记忆、长期知识的区别 | 任务恢复信息模型 |
| 2 | 决策机制与自主权边界 | 明确自主执行、澄清、批准和阻塞的边界 | 决策分类表 |
| 3 | 可靠性与错误处理 | 理解重试、幂等、恢复和失败处理 | 故障场景与处理矩阵 |
| 4 | 可观测性与运行日志 | 理解日志、审计和证据的区别 | 最小事件记录模型 |
| 5 | 质量评价 | 建立合理的质量指标和统计口径 | 初始评价指标表 |
| 6 | 人机协作与权限管理 | 明确角色、任务、工具和资源权限 | 风险分级与批准规则 |
| 7 | 可扩展性与平台解耦 | 理解模块化、多角色和平台适配 | 架构演进草图 |

## 6. 当前阶段的建议

不建议一次性实现以上七类能力，也不建议为了架构完整而立即扩展代码。

建议采取以下节奏：

### 第一阶段：先理解和定义

- 重点学习工作记忆与上下文管理。
- 梳理现有 task.json、history、submission 和交付物分别保存了什么信息。
- 明确任务恢复时的最小必要信息。
- 暂不修改状态机和 Python 程序。

### 第二阶段：从真实使用问题出发

在本地测试和真实任务中记录：

- 是否发生会话中断后无法接续。
- 是否出现重复执行或重复提交。
- 是否发生 Agent 自行猜测输入或越权操作。
- 是否缺少关键过程记录。
- 返工主要发生在哪个环节。

### 第三阶段：只解决已证实的问题

根据实际问题选择最小改进：

- 若上下文恢复困难，先改进任务执行摘要和恢复检查。
- 若重复执行，先设计操作级幂等策略。
- 若决策边界不清，补充人工批准和阻塞规则。
- 若问题无法追溯，补充最小事件记录。
- 若 A/B 职责确实出现瓶颈，再讨论新增角色。

任何涉及代码、Schema、状态机或平台配置的改动，都应单独评估范围、收益、风险和验证方法。

## 10. 当前 Generic Dual-Agent 项目的核心架构与运行机制

本节从当前 V1.2 项目的实际实现出发，说明系统由哪些组件组成、组件之间如何配合，以及一项任务在 WorkBuddy 和本地程序中如何流转。它描述的是当前项目，不是未来自动化架构的设想。

### 10.1 先用一句话理解当前架构

当前系统可以理解为：

**WorkBuddy 负责运行两个有明确分工的 AI Agent；本地任务文件负责保存双方共享的任务事实；Python 程序负责把关键状态转换和数据校验规则真正执行起来；用户负责在 A、B 两个独立专家会话之间进行人工交接。**

因此，它不是一个持续运行、自动派发任务的后台服务，而是一个由 AI Agent、文件协议和本地命令行程序共同组成的半自动协作框架。

### 10.2 核心架构图

```text
                         用户
              提出需求 / 澄清 / 人工交接
                         |
             +-----------+-----------+
             |                       |
             v                       v
    WorkBuddy 专家会话 A      WorkBuddy 专家会话 B
    Agent A                  Agent B
    任务管理与验收             任务执行与自检
    - 理解和澄清需求           - 读取任务定义
    - 拆解和定义任务           - 检查输入与约束
    - 制定验收标准             - 执行具体工作
    - 跟踪状态                 - 生成交付物
    - 独立验收                 - 自检并提交
             |                       |
             +-----------+-----------+
                         |
                         v
             本地文件系统 / 任务工作区
                  tasks/TASK-xxx/
             +-------------------------+
             | task.json               |
             | 任务状态与定义的权威源   |
             | task.md                 |
             | 人类可读的任务视图       |
             | inputs/                 |
             | 输入材料                 |
             | deliverables/           |
             | B 的交付物               |
             | self-check.md           |
             | B 的自检记录             |
             | submission.json         |
             | B 的结构化提交           |
             | acceptance.md           |
             | A 的验收记录             |
             | history/                |
             | 状态转换审计记录与快照   |
             +-------------------------+
                         ^
                         |
             Agent A / B 按需要调用
                         |
                         v
             Python 状态管理程序
             scripts/task_state.py
             - 创建任务
             - 校验任务结构
             - 检查状态转换是否合法
             - 检查角色参数与转换权限
             - 执行提交/验收门禁
             - 保护基线和文件路径
             - 锁定并发状态转换
             - 原子写入、审计与恢复
                         |
             +-----------+-----------+
             |           |           |
             v           v           v
        JSON Schema    templates/   tests/
        数据结构规则    文件模板      自动化测试
```

图中最重要的关系是：**A 和 B 不直接通过自动消息接口互相调用，而是围绕同一份任务工作区协作；Python 程序不替 Agent 做专业工作，而是检查任务流程和数据规则。**

### 10.3 各组件分别负责什么

| 组件 | 所在位置 / 载体 | 主要职责 | 不负责什么 |
|---|---|---|---|
| WorkBuddy 平台 | WorkBuddy | 提供 AI 专家会话、模型运行环境和工具使用入口 | 当前版本不负责自动编排 A/B 的完整任务生命周期 |
| Agent A | WorkBuddy 自定义专家 `dual-agent-a` | 需求理解、澄清、任务定义、任务跟踪、独立验收和返工决策 | 不代替 B 完成任务主体工作，不修改 B 的交付物 |
| Agent B | WorkBuddy 自定义专家 `dual-agent-b` | 读取任务、执行工作、自检、整理证据、提交交付物和报告阻塞 | 不修改任务目标/验收标准，不自行宣布验收通过 |
| 角色指令与协作规范 | `agents/`、WorkBuddy 专家配置、`docs/` | 告诉 A/B 各自是谁、应该做什么、不能做什么，以及如何遵循协议 | 文字约定本身不是平台级身份认证或工具权限隔离 |
| 任务工作区 | `tasks/TASK-xxx/` | 保存一项任务从定义、执行、提交到验收的全部持久化资料 | 不保存 Agent 完整的内部推理过程 |
| `task.json` | 每个任务目录 | 机器可读的任务定义和状态权威源，保存状态、验收标准、历史等 | 不适合作为主要的人类阅读界面 |
| `task.md` | 每个任务目录 | 将任务信息整理为便于人阅读的视图 | 不是状态权威源；与 task.json 冲突时以 task.json 为准 |
| `inputs/` | 每个任务目录 | 保存 A 提供给 B 的输入材料或输入副本 | B 不应擅自改变输入的确认状态或任务定义 |
| `deliverables/` | 每个任务目录 | 保存 B 实际产出的文件 | A 只检查和验收，不代替 B 修改 |
| `self-check.md` | 每个任务目录 | 记录 B 对完整性、正确性、一致性、边界条件、可追溯性和交付质量的自检 | 自检报告不能替代 A 的独立验收 |
| `submission.json` | 每个任务目录 | 以结构化形式汇总交付物、自检结果、验证方法、证据和遗留问题 | B 的提交声明不等于验收通过 |
| `acceptance.md` | 每个任务目录 | 记录 A 对各项验收标准的检查结果、证据、结论和返工要求 | 不应为了通过验收而放宽已冻结的标准 |
| `history/` 与 `baseline.json` | 每个任务目录 | 保存状态转换快照、审计信息和 READY 时建立的验收基线 | 不等于完整的 Agent 活动日志，也不能证明技术结论本身正确 |
| Python 状态管理程序 | `scripts/task_state.py` | 对任务创建、结构校验、状态转换、门禁、路径安全、锁、原子写入和审计恢复执行程序级检查 | 不执行 BMS 专业分析，也不判断所有交付物的技术内容是否正确 |
| JSON Schema | `schemas/task-schema.json` | 定义 task.json 的字段、类型、必填项和枚举等机器校验规则 | 不负责 Agent 的自然语言工作流程 |
| 模板 | `templates/` | 提供任务视图、自检、提交和验收文件的统一格式 | 模板本身不会自动完成填写和判断 |
| 测试 | `tests/`、GitHub Actions | 验证程序的状态规则、安全检查、异常恢复和回归行为 | Python 测试通过不等于 WorkBuddy 中的模型行为已全部验证 |

### 10.4 系统中有三类不同的“规则”

理解当前架构时，尤其要区分以下三类规则：

1. **Agent 行为规则**：由 A/B 角色指令和协作文档规定。例如 A 负责验收、B 负责执行，B 不得修改验收标准。这类规则主要约束模型行为。
2. **程序强制规则**：由 `task_state.py`、JSON Schema 和状态机实现。例如不允许非法状态转换、验收不满足门禁时拒绝 ACCEPTED。这类规则由代码执行。
3. **平台实际权限**：由 WorkBuddy 和操作系统决定 Agent 实际能调用哪些工具、访问哪些文件。当前任务中的 `authorized_tools` 是任务授权声明，不自动成为 WorkBuddy 的工具权限代理。

三类规则相互配合，但不能互相替代。特别是，角色指令写着“B 不能做某事”，不等于平台技术上绝对阻止 B；命令中的 `--actor B` 也是调用者声明，不是对模型真实身份的认证。

### 10.5 一项任务是如何运行的

当前正常任务链路如下：

```text
用户提出任务
    |
    v
Agent A 理解需求、识别输入和约束
    |
    +---- 需求不清楚 ----> NEEDS_CLARIFICATION
    |                         |
    |                    用户补充信息
    |                         |
    +<------------------------+
    |
    v
A 创建任务：DRAFT
    |
    v
A 补全 task.json
目标 / 输入 / 约束 / 交付物 / 验收标准 / 验证计划
    |
    v
A 调用状态管理程序转换为 READY
程序校验任务结构、验收标准和交付物定义，并建立验收基线
    |
    v
用户将任务工作区交给 Agent B（人工交接）
    |
    v
B 读取 task.json / task.md / inputs/
检查目标、状态、输入、约束、授权和验收标准
    |
    v
B 调用程序转换为 IN_PROGRESS
    |
    v
B 执行任务，生成 deliverables/
    |
    v
B 完成 self-check.md
    |
    v
B 写入 submission.json
    |
    v
B 调用程序转换为 SUBMITTED
程序检查提交结构、自检报告和相关一致性
    |
    v
用户将任务和提交结果交回 Agent A（人工交接）
    |
    v
A 检查交付物、证据和每一条验收标准
    |
    +---- 全部通过 ----> ACCEPTED
    |
    +---- 存在失败项 --> REWORK --> B 修改、复验、重新提交
    |
    +---- 无法继续 ----> BLOCKED
```

状态转换的核心路径是：

`DRAFT → READY → IN_PROGRESS → SELF_CHECK → SUBMITTED → ACCEPTED`

如果验收不通过，会进入 `REWORK`，由 B 按照 A 给出的失败项和复验要求返工；达到返工上限或无法安全继续时，可能进入 `BLOCKED`。关键输入不完整时则应先澄清，而不是让 B 自行猜测。

### 10.6 Python 程序在运行链路中的位置

Python 程序是一个**本地命令行工具（CLI）**，不是后台常驻服务。A 或 B 在需要创建任务、推进状态或检查任务时调用它；每次命令启动一个 Python 进程，完成当前操作后退出。

当前主要子命令包括：

| 命令 | 用途 | 典型使用时机 |
|---|---|---|
| `init` | 创建任务目录和初始任务文件，初始状态为 DRAFT | A 创建新任务 |
| `transition` | 校验并执行合法状态转换，更新 task.json 并留痕 | A/B 推进任务状态 |
| `validate` | 校验任务文件结构 | 检查任务定义是否符合 Schema |
| `status` | 查看任务状态总览 | A 跟踪任务 |
| `check-submission` | 检查提交信息与任务验收标准的一致性 | A 验收前检查 |
| `audit-recover` | 检查并恢复可安全恢复的审计快照 | 状态转换异常或提示需要恢复时 |

Windows PowerShell 环境下，用户本地执行命令时使用 `py` 启动器。示意如下（需先进入本地仓库目录，并按 README 安装依赖）：

```powershell
# 安装 JSON Schema 校验依赖
py -m pip install jsonschema

# 创建任务
py scripts/task_state.py init --id TASK-001 --title "示例任务" --objective "完成一项可验证的工作" --type generic

# 查看任务状态
py scripts/task_state.py status

# 将任务推进到 READY（前提是已补齐 task.json 中的任务定义）
py scripts/task_state.py transition --id TASK-001 --to READY --actor A --note "任务定义完成"

# B 开始执行
py scripts/task_state.py transition --id TASK-001 --to IN_PROGRESS --actor B --note "开始执行"

# 检查审计快照
py scripts/task_state.py audit-recover --id TASK-001
```

以上命令用于说明程序的调用方式；完整任务运行还需要 A/B 按协议填写任务定义、自检、提交和验收文件。不能只运行几条命令就认为整个任务已经完成。

### 10.7 一次状态转换在程序内部做了什么

以 `READY → IN_PROGRESS` 为例：

1. 命令行解析器读取任务 ID、目标状态、调用角色和备注。
2. 程序检查任务 ID 和任务目录是否合法。
3. 获取该任务自己的转换锁，避免两个进程同时修改同一任务状态。
4. 重新读取权威文件 task.json。
5. 检查任务结构、当前状态、目标状态以及状态转换是否合法。
6. 检查当前转换是否允许声明的角色执行。
7. 执行目标状态对应的专属门禁。
8. 更新内存中的状态、更新时间和 history。
9. 通过原子写入保存 task.json，并按需要生成或完成审计快照。
10. 输出成功或失败信息；命令结束，进程退出。

这说明 Python 程序承担的是**流程控制与数据完整性检查**。它不会替 B 生成技术报告，也不会替 A 阅读专业证据并作出真正的工程判断。

### 10.8 当前架构的自动化程度

| 环节 | 当前方式 | 当前能力判断 |
|---|---|---|
| A 理解用户需求和规划任务 | Agent 在 WorkBuddy 会话中完成 | AI 执行，用户可澄清 |
| 创建任务文件 | A 按规范调用本地程序并填写任务文件 | 半自动 |
| 状态转换与结构门禁 | Python 程序执行 | 程序自动校验 |
| A 将任务交给 B | 用户切换专家/会话并确保任务文件可访问 | 人工交接 |
| B 执行、自检和生成交付物 | Agent B 在 WorkBuddy 中完成 | AI 执行，质量需证据验证 |
| B 将提交交回 A | 用户切换回 A 并确保提交文件可访问 | 人工交接 |
| A 独立验收 | Agent A 按标准检查并填写验收记录 | AI 判断 + 程序门禁 |
| 后台调度、自动唤醒另一个 Agent | 当前没有实现 | 不支持/未实现 |
| Agent 真实身份认证和全面工具权限代理 | 当前没有实现 | 不支持/未实现 |

### 10.9 当前架构的能力边界

当前项目已经具备一个可运行的任务管理与质量门禁骨架，但仍需明确以下边界：

- **没有自动 Agent-to-Agent 调用**：A 不会通过本框架代码自动启动 B，B 也不会自动通知 A；用户负责切换专家和交接。
- **没有后台任务调度器**：Python 程序由命令触发，不会在后台持续监听任务。
- **任务状态不等于模型上下文**：task.json、history 和交付物可以帮助恢复任务事实，但不会自动恢复上次会话的全部推理过程。
- **角色约定不等于身份认证**：`--actor A/B` 是程序调用参数，不能证明实际调用者就是对应 Agent。
- **任务授权不等于工具权限**：`authorized_tools` 描述任务允许范围，但平台实际工具权限仍由 WorkBuddy 等运行环境控制。
- **程序门禁不等于专业正确性证明**：程序可以检查文件、字段、状态和证据路径，但不能仅凭结构校验保证 BMS 电路设计、WCCA、DFMEA 或其他工程结论正确。
- **测试通过不等于平台集成全部验证**：Python 自动化测试证明的是被测试的程序行为；真实 WorkBuddy 会话中的角色遵循、文件访问和人工交接仍需要本地测试。

### 10.10 阅读当前项目时建议记住的四句话

1. **A 管任务，B 做任务，用户负责当前版本的人工交接。**
2. **任务目录是双方共享的工作现场，task.json 是任务状态的权威记录。**
3. **Python 程序管流程和结构门禁，不替代 Agent 的专业判断。**
4. **当前是文件驱动、人工交接、程序辅助约束的半自动双 Agent 框架，不是自动调度的多 Agent 平台。**
